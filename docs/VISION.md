# VISION：Rich Markdown 愿景书

> **读者**：所有人（决策者、开发者、AI 工具用户、潜在贡献者）
> **阅读时长**：6–10 分钟
> **最近更新**：2026-05-10

## 一句话定义

**Rich Markdown（`.rmd`）是一种 100% 兼容 Markdown 的轻量富文档格式：写起来像 Markdown 一样省 token、好 diff，渲染出来像 HTML 一样丰富、可交互、一个链接就能分享，而且让人在 AI 协作中始终"留在循环里"。**

## 我要解决的真实矛盾

AI 生产文档的时代，主流格式被夹在两个不舒服的极端之间：

**Markdown 太瘦。**
它擅长正文、标题、列表，但表达不了图表、布局、滑块、流程图。AI 想"展示一张柱状图"只能拿 ASCII 凑，想"传达一个颜色"只能用 Unicode 色块估。**当一份计划超过一百行，人就不再读了——而 AI 写的计划越来越长。** 结果是：信息密度低、视觉粗糙、无法交互。

**HTML 太胖。**
它什么都能做，代价具体而真实：token 用量大 2–4 倍，生成慢 2–4 倍，diff 噪声满屏，版本管理痛苦。AI 用 HTML 输出 PR 解释或代码审查时容易在 `<div>` 嵌套里走丢，人也很难在 GitHub 上看清改动。

**两者中间是一片真实的设计空白。**
MDX、AsciiDoc、Quarto、Typst 都试图填补它，但**没有一个是为"AI agent 直接生产文档"这个时代设计的**——它们都假设了一个会亲手编辑、会逐字阅读的人类作者。

## 更深一层：当人不再编辑文档

AI 协作正在悄悄改变文档的使用方式：

- 文档越来越多是 AI 写的、AI 改的，**人类的角色变成"读者 + 决策者 + 偶尔的指挥者"**。
- "人类容易手写"这个 Markdown 二十年来的核心卖点，在 AI 协作中已经不再是优势。
- 真正稀缺的资源变成了：**人是否愿意读、读得动多少、读完能不能反馈、反馈能不能回到 AI 手里**。

这意味着评估文档格式的标准变了：

| 评估维度 | 过去（人写人看） | 现在（AI 写人看） |
|---|---|---|
| 编写门槛 | 极重要（决定谁能写） | 不重要（AI 不在乎语法） |
| 阅读体验 | 重要 | **极重要**（决定人是否会真读） |
| 信息密度 | 一般 | **极重要**（决定 100 行能装多少东西） |
| 可交互 | 不重要 | **极重要**（让人重新进入循环） |
| 可分享 | 一般 | **极重要**（AI 产出量大，分享是常态） |
| 版本控制友好 | 重要 | 重要（Git 仍然是基础设施） |
| token 经济 | 不存在 | **新维度**（每天千万次生成的总账） |

Markdown 在旧标准下是优等生，在新标准下只及格一半。HTML 在新标准下高分项明显，但在版本控制和 token 经济两栏不及格。

**我要造一个在新标准上每一项都及格、并且在"信息密度 / 交互 / 分享 / token 经济"上拿到优秀的格式。**

## 我的愿景

**让每一个 AI agent 输出的文档，都默认拥有图表、布局、交互和可分享链接的能力——而代价仅比纯 Markdown 高一点点，diff 仍然干净，人始终留在循环中。**

具体来说，三年后我希望看到这样的世界：

1. 打开 Claude Code、Codex、Cherry Studio 等桌面 AI 客户端，让它"写一份方案对比"，它会自动产出一份 `.rmd`：左右双栏、嵌入图表、底部带一个可调的 slider 让你立刻试参数、再下面一个"复制为提示词"的按钮，让你把调好的状态直接传回 AI。
2. 同一份 `.rmd` 文件，通过不同的渲染器主题，可以在浏览器里呈现为科技风暗色仪表盘、纸质感学术报告、Notion 风协作笔记。源文件不变，视觉风格自由切换，零额外 token 成本。
3. 类似 Obsidian 的 `.rmd` 客户端，支持本地编辑、双向链接、主题市场、一键发布到 `rmd.sh/abc123` 短链分享。源文件几 KB，加载即开。
4. `.rmd` 成为 AI agent 输出文档的"默认富文本格式"——就像 JSON 之于 API、Markdown 之于 README 一样自然。

## 谁会因此受益

| 角色 | 今天的痛点 | `.rmd` 带来的改变 |
|---|---|---|
| **AI 用户** | AI 输出要么粗糙（md），要么冗长不能分享、不能审查（html） | 既好读又能交互、能分享、能审查的"活文档" |
| **AI 客户端开发者** | 想增强表现力只能教 AI 写 HTML，token 暴涨、diff 失控 | 接入一个 skill / 插件，AI 输出立刻富起来，diff 仍干净 |
| **PR 审查者 / 工程团队** | HTML 文件在 GitHub diff 里几乎没法看 | rmd 源文件接近 markdown，diff 清晰；同时 PR 摘要可以是富 HTML |
| **创作者 / 研究者** | Markdown 不够表达，HTML 太重 | 写法仍是熟悉的 md，但能轻松嵌入图表、对比、流程 |
| **企业知识管理** | 文档静态、风格不统一、改个主题要重写 | 一份源文件，全公司用统一主题渲染；交互件让文档"会动" |

## 核心价值主张

我用五件事和市面上所有方案区分开：

### 1. 源文件极简，渲染层做重活
AI 写的是声明式的"意图"——一行 `:::chart bar` 就够了——渲染器把意图翻译成富视觉。这继承了 Markdown "`# 标题` 五字符表达完整语义"的成功基因，也避免了 HTML 那种"开标签 + 闭标签 + 一堆属性"的三段式累赘。

### 2. token 经济，每一行都算钱
2026 年的现实是：Claude Pro 的对话有额度上限、API 按 token 计费、企业部署的月度账单一栏栏都是真金白银。**让 AI 输出富文档的代价从"HTML 那么贵"降到"Markdown 那么便宜"，这是用户每天打开账单都能感受到的价值，不是抽象指标。** 我的目标：在四类典型富文档（方案对比 / PR 解释器 / 原型调参 / 研究简报）上，token 用量做到 HTML 方案的 1/4 到 1/8、生成时间相应减少 2–4 倍。这意味着同样的额度能多对话 2–4 倍，同样的成本能服务 2–4 倍的用户。

### 3. 一份源文件，多种主题渲染
同一个 `.rmd` 文件，在 `tech-dark` 主题下是赛博仪表盘，在 `paper` 主题下是学术稿件，在 `notion-like` 主题下是协作文档。**风格属于渲染器和用户，不属于源文件**——AI 不需要每次重新发明视觉规范，用户也不需要被原作者的审美绑死。

### 4. 为 AI agent 而生
所有语法设计都遵循"AI 一次写对、token 最省、diff 最干净"三个标准。配套提供 Claude Code / Codex / Cherry Studio 等主流桌面工具的 skill / 插件，零摩擦接入，立刻生效。

### 5. 保持人在循环中
AI 越能干，人越容易"放手"——不读计划、默认接受、逐渐失去判断。我认为这是 AI 协作里最危险的隐性成本。`.rmd` 把"双向交互"做成一等公民——`:::slider`、`:::tabs`、`:::export` 是关键字而非每次重新发明的 HTML/JS 模板。**目标是：人和 AI 协作越深，反而越觉得自己 in control，而不是越觉得被牵着走。**

## 关于 token 的论证（为什么这事在 2026 年仍然要紧）

业内有一种流行说法：在百万级上下文窗口下，单文档多用几千 token "在上下文中并不明显"，因此 token 优化不再重要。我尊重这个观察，但**不接受由此推出的"token 不重要"结论**。原因有四：

**一、用户感受到的不是"上下文比例"，而是"账单"和"额度"。**
Claude Pro 用户能直接看到对话额度被一份富 HTML 报告吃掉一大块；API 用户每月账单上的输出 token 一栏，HTML 方案就是 4 倍；企业部署里，客服 / 研究 / 报告这类高频场景每篇多 2-4 倍 token，乘以日活量就是六位数美金的差距。这不是"上下文窗口里看不见"的事，是月底打开账单时立刻看见的事。

**二、并非所有人都用旗舰模型。**
Sonnet、Haiku 以及更小的本地模型有更窄的上下文、更敏感的成本结构。要让"富文档"普及到所有 AI 客户端而不只是顶配场景，token 效率是准入门槛，不是奢侈品。

**三、生成时间和延迟也是 token 的函数。**
HTML 通常比 Markdown 慢 2–4 倍。在交互式 agent 场景里，这种延迟直接吃掉用户耐心。`.rmd` 把图表、布局这些"贵的部分"声明化，AI 只需要写极短的意图，吐字速度立刻接近 Markdown。

**四、token 节省可以和别的优势叠加，而不是互斥。**
HTML 的代价是"贵 + diff 嘈杂 + 风格固化在源码里"。`.rmd` 同时解决这三件事：**省 token、保留 diff 干净、把风格交给主题**。这是 HTML 给不出的组合拳。

所以我的定位很明确：**token 经济是 `.rmd` 的核心价值之一，与"主题切换"、"原生交互"、"diff 干净"并列，而不是它们的副产品。** 我不假装这件事不重要，相反——这是用户最先感受到、也最不可能回头的价值。

## 成功的样子（可量化的信号）

短期（6 个月）：

## 这个项目"不是什么"（划清边界）

- **不是新一代标记语言。** Markdown 仍是底座，所有合法 md 都是合法 rmd。我只在围栏块上做扩展。
- **不是 WYSIWYG 富文本编辑器。** 源文件是文本，目标是 AI 友好；WYSIWYG 编辑器是后续客户端的事，不是格式本身的目标。
- **不是企业级文档平台。** 我做格式和渲染器，不做权限、协作、审计这些重型功能。
- **不试图替代 Notion / Obsidian / Confluence。** 它们是产品，我是格式 + 工具链。两者可以共存，甚至被它们集成。

## 我的赌注

我赌五件事是对的：

1. **AI 生产的文档量级会继续指数增长**——文档从"人写人看"逐渐变成"AI 写人看"，格式必须为 AI 优化。
2. **token 成本在可见的未来仍然是用户决策因子**——模型会变便宜，但 AI 用量增长更快，账单和额度的痛在未来 3–5 年只会更明显，不会更弱。优化 token 经济的工具不会过时。
3. **人的"控制感"是 AI 协作中最稀缺的资源**——所有用 AI agent 的人都在悄悄经历"放手太多"的焦虑。能找回控制感的工具会赢。
4. **"源文件 + 渲染器 + 主题"的三段式比"全包式 HTML"更适合 AI 时代**——AI 写意图，工具决定呈现，用户选择风格、保留 diff、保留分享便利。
5. **Markdown 的工程友好度 + HTML 的表现力 + 原生交互 + token 经济**这个组合，没有任何现有方案完整提供——MDX 缺主题、Notion 缺源文件、HTML 缺 diff 且贵、纯 md 缺一切——这正是机会。

如果这五个判断成立，`.rmd` 有机会成为 AI 时代的 Markdown。
