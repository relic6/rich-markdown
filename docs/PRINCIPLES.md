# PRINCIPLES：Rich Markdown 设计原则

> **读者**：核心团队、长期贡献者、任何要在 `.rmd` 上做技术决策的人
> **阅读时长**：10–15 分钟
> **最近更新**：2026-05-10

## 这份文档是用来做什么的

VISION 回答了"我们要去哪儿"。PRINCIPLES 回答的是"路上每一步要遵守什么规矩"。

这不是哲学声明，是**规则书**：

- 任何设计争论必须先回到这里。"我觉得这样比较好"不是论据，"这违反原则 P3 但能让 P5 提升 50%"才是。
- **原则可以被推翻**，但必须走"例外协议"——明确写下例外的范围、原因、有效期，并归档到 ADR。没有 ADR 的违反一律视为 bug。
- 优先级有明确次序（见 §3）。当两条原则打架，按矩阵裁。

## 1. 心智模型：三层架构

`.rmd` 在概念上有三层，每一条原则都明确归属其中一层：

```
┌──────────────────────────────────────────┐
│  渲染层（Renderer / Theme）              │  P6, P7, P8
│  - 把意图翻译成 HTML/CSS/JS              │
│  - 负责所有视觉、交互、计算              │
├──────────────────────────────────────────┤
│  解析层（Parser / AST）                  │  P3, P4
│  - 把 .rmd 文本变成结构化数据            │
│  - 负责语法规范、错误恢复                │
├──────────────────────────────────────────┤
│  源文件（Source）                        │  P1, P2, P5
│  - 纯文本 .rmd 文件                      │
│  - 由 AI 写、人读、Git 管                │
└──────────────────────────────────────────┘
```

跨层修改成本极高。原则的存在就是为了**保证每一层只解决它该解决的问题**。

## 2. 八条核心原则

### P1 — 100% 向下兼容 CommonMark

**陈述**：任何合法的 CommonMark 文档必须是合法的 `.rmd` 文档，且渲染结果必须保留 CommonMark 的语义和视觉等价性。

**为什么**：Markdown 已经赢了。我们继承生态、AI 训练数据、用户肌肉记忆，是因为我们站在 Markdown 上，而不是替代它。任何破坏兼容性的设计都等于自断右臂。

**含义**：
- 所有扩展只能通过"围栏块"`:::` 和 frontmatter 实现，不能改任何 CommonMark 标点的含义。
- 任何 `.rmd` 渲染器必须先通过完整的 CommonMark spec 测试。
- 用户用 `.md` 文件后缀也能被 `.rmd` 渲染器正常处理。
- **反例**：把 `**bold**` 重新定义为"重要标记"并加额外样式 → 破坏兼容，否决。

### P2 — diff 干净是硬约束

**陈述**：任何 `.rmd` 源文件的"语义性单点修改"，在 Git diff 中必须只产生与该修改对应的最小行变化。不允许任何会引入大面积自动重排的语法或工具行为。

**为什么**：HTML 最大的代价不是 token，是 diff 嘈杂。我们的工程友好度是核心卖点，diff 一旦失控，所有"AI 帮你改文档"的工作流都会塌。

**含义**：
- 不引入自动 ID 生成、自动重新格式化、自动属性补全等会让单字符修改扩散到多行的机制。
- 块的属性顺序、空白、引号种类必须**宽容解析、保守输出**——AI 写得乱也能解析，但格式化工具不能擅自重排已有内容。
- **反例**：在保存时按字母顺序重排所有属性 → 修改一个属性导致全行重写，否决。

### P3 — 源文件极简：表达意图，不表达实现

**陈述**：源文件中的每个块只表达"这是什么"，不表达"如何渲染"。视觉、交互、计算逻辑全部下沉到渲染层。

**为什么**：Markdown 之所以赢，不是因为它"能写富文本"，而是因为它"用 5 个字符表达完整语义"。我们继承这个基因。

**含义**：
- 块语法不允许出现颜色值、像素尺寸、字体名等表现层属性。
- 数据描述（`:::chart bar` 加几行数字）和表现描述（什么颜色、什么动画）必须解耦。
- 如果一个块只能在某种特定视觉风格下成立，它就违反了这条原则。
- **反例**：`:::chart bar color=#ff0000 width=600px` → 颜色和尺寸是渲染层的事，否决。改成 `:::chart bar emphasis=primary`，由主题决定 primary 是什么颜色。

### P4 — AI 一次写对优先于人写得舒服

**陈述**：所有语法设计的首要评估对象是大语言模型，而不是人。如果一种写法 LLM 在零示例情况下出错率超过 5%，必须重新设计。

**为什么**：`.rmd` 主要由 AI 生产。人的偏好（比如 YAML 的缩进美感、JSON 的引号风格）如果增加 AI 出错概率，就是设计错误。

**含义**：
- 优先选择"前缀关键字 + 自由文本"的语法（`:::chart bar`），避免严格的属性顺序、复杂转义规则。
- 容错优先：解析器对引号缺失、空白多余、属性顺序变化必须宽容。
- **每个新块必须做一次"零示例测试"**：用至少 3 个主流模型在没看过文档的情况下生成，错误率必须 ≤ 5%。
- **反例**：`:::chart {"type": "bar", "options": {"strict": true}}` → JSON 易错且冗长，否决。

### P5 — token 优势必须可证明且 ≥ 3×

**陈述**：每个候选进入核心规范的新块，必须在至少一个典型场景下证明 token 用量 ≤ 同等表现力 HTML/SVG 实现的 1/3。否则只能进 `experimental` 或第三方扩展。

**为什么**：`.rmd` 的承诺之一是 token 经济。如果某个块连这条都做不到，它没有理由不直接用 HTML。

**含义**：
- 每个新块的提案必须附带：典型用例、对应的 HTML 等价实现、token 数对比表。
- 渲染器自动产生的 HTML 不计入 `.rmd` 源文件的 token 数（这正是 P3 的目的）。
- **反例**：一个 `:::callout` 块如果只比 `> ` 引用块多一个图标，token 优势 < 3×，应该并入 markdown 引用语法的扩展属性，而不是另立块。

### P6 — 主题只能改样式，不能改语义

**陈述**：主题的能力边界是 CSS、字体、配色、动画时长、布局密度。**主题不能改变内容、不能改变交互行为、不能注入或删除 DOM 节点的语义角色**。

**为什么**：如果主题能改语义，"一份源文件多种主题"就崩了——同一份 `.rmd` 在不同主题下变成不同的文档，分享和审查都失去意义。

**含义**：
- 主题接口是 CSS 变量 + 槽位（slot），不是模板覆盖。
- 主题不能注册新块、不能拦截事件、不能改变 `:::export` 复制出去的内容。
- 主题可以隐藏某些元素（视觉简化），但不能修改它们的内容或交互结果。
- **反例**：一个"极简主题"把所有 `:::chart` 替换成纯文本表格 → 改了语义和可视化形态，否决。改成 CSS 隐藏图表显示文本是允许的，因为内容未变。

### P7 — 交互是一等公民

**陈述**：`:::slider`、`:::tabs`、`:::export`、`:::diff` 等"让人重新参与文档"的能力是核心规范的一部分，不是可选扩展。

**为什么**：`.rmd` 区别于 Markdown 和 MDX 的关键不是"更好看"，而是"让人能重新进入循环"。如果交互被降级为可选项，渲染器实现可以不支持，整个差异化卖点就消失。

**含义**：
- 核心规范定义至少 3 类交互块：参数调节（slider/select）、视图切换（tabs/accordion）、回流（export/copy）。
- 任何符合 spec 的渲染器必须实现这 3 类，否则不能称为"完整渲染器"。
- 这些块的 fallback 行为也要明确：在静态 PDF / 邮件等不支持 JS 的环境下，必须降级为可读的静态形式。

### P8 — 失败优雅降级，永远可读

**陈述**：任何 `.rmd` 文档在任何环境下打开，必须至少是"可读的纯文本 + 可读的 markdown"。不认识的块不能让整个文档崩溃或变成乱码。

**为什么**：兼容性的真正考验不是渲染器实现得多好，而是渲染器**没**实现某个块时会发生什么。优雅降级是用户对我们的最低信任——他们必须相信"打开总不会出事"。

**含义**：
- 解析器遇到不认识的 `:::xxx` 块，必须把块内容当作 code block 显示，附小提示"此块需要 xxx 渲染器"。
- 在不支持 JS 的环境（邮件、纯 HTML 导出、终端预览）下，所有交互块必须降级为静态展示 + 链接（如"在浏览器打开以交互"）。
- 渲染器升级或降级，旧文档必须仍然可打开。**反例**：v0.3 的某个块在 v0.2 渲染器里直接 throw → 否决，必须降级到 code block。

## 3. 优先级矩阵（冲突时怎么裁）

原则会打架。下面是明确的偏序——**上面的赢下面的**：

```
P1 (CommonMark 兼容)
   └── 一切之上。破坏兼容直接否决。

P2 (diff 干净)
   └── 凌驾于表达力之上。再炫的语法导致 diff 脏，砍掉。

P8 (优雅降级)
   └── 凌驾于功能完整之上。先保证不崩，再谈做得多好。

P6 (主题不改语义)
   └── 凌驾于主题表现力之上。主题不能用"功能强大"换"语义混乱"。

P3 (源文件极简)  ⇄  P7 (交互是一等公民)
   └── 互相制衡。新交互块必须先证明它的"意图描述"足够极简（P3），
       否则可以选择不进核心。

P4 (AI 一次写对)  ⇄  P5 (token 优势 ≥3×)
   └── 互相制衡。语法可以为 token 优化让步一点点可读性，
       但不能让 AI 错误率超过 5%。

P7 (交互一等公民)  ⇄  P5 (token 优势 ≥3×)
   └── 互相制衡。交互块允许 token 优势放宽到 ≥2×，因为它们的价值
       不只在 token，在"找回控制感"。
```

**记忆口诀**：兼容 > 干净 > 安全（降级）> 一致（主题语义）> 经济与表达的平衡。

## 4. 加新东西的"准入测试"

任何新增块、新增 frontmatter 字段、新增主题接口，提案 PR 必须答完以下 7 题，缺一不可：

| # | 问题 | 验收方式 |
|---|---|---|
| 1 | 这是什么意图？为什么不能用现有块？ | 文字说明 + 反例 |
| 2 | 不写这个块时，用 HTML 至少要多少 token？ | 真实代码对比 |
| 3 | 写这个块要多少 token？token 优势 ≥ 3×？ | 数字表格（受 P5 约束）|
| 4 | 主流 LLM 零示例错误率 ≤ 5%？ | 至少 3 模型 × 10 样本测试 |
| 5 | 在不支持此块的渲染器里如何降级？ | 实际 fallback 截图 |
| 6 | 主题能影响它什么？不能影响什么？ | 列出主题接口契约 |
| 7 | 它的 diff 行为如何？修改一个属性影响多少行？ | 示例 diff |

任何一题答不出来，提案打回。

## 5. 例外协议

原则不是法律，但破坏原则必须可见、可追溯、可回滚：

1. **走 ADR**：写一篇 `adr/NNNN-exception-Pn-xxxxx.md`，说明：
   - 违反哪条原则
   - 为什么本次必须违反
   - 影响范围（哪些块 / 哪些渲染器 / 哪些版本）
   - 退出条件（什么情况下可以回到原则）
2. **打标签**：违反原则的代码必须在源码里加 `// rmd:exception P3 see adr/0042` 注释。
3. **核心团队评审**：例外不是 PR reviewer 个人能批的，必须 ≥ 2 位核心维护者签字。
4. **定期复审**：每个例外每 6 个月复审一次，要么转正（修订原则）要么消除（修复实现）。

**没有走例外协议的违反，都是 bug，会被回滚。**

## 6. 不在原则里的事（为什么）

我们刻意没把以下当原则，避免把规则书写成圣经：

- **"美观"** —— 主观且无法验收，由主题市场和用户投票决定。
- **"完备"** —— 我们不追求覆盖所有富文档需求。MDX 想做的事不是我们的事。
- **"性能"** —— 重要但不是原则，是工程目标，写在 `ARCHITECTURE.md` 里。
- **"易学"** —— 由 P4 间接保证（AI 一次写对意味着对人也不会太难学）。

## 7. 这份文档的修订规则

- 修订原则本身是**本仓库最高级别的变更**，必须 ≥ 3 位核心维护者签字 + 公开 RFC 至少 14 天。
- 增加新原则比修改旧原则容易，鼓励先加再合并。
- 任何 ADR 累计违反同一原则 ≥ 3 次时，自动触发该原则的复审。
